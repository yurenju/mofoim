# 聲調可以不打，由引擎依前後文猜

ADR 0003 規定每個音節的最後一個鍵一定是聲調鍵，因為它是「這個字到這裡結束」唯一可靠的記號。代價是每個字都要多按一個鍵，約占全部按鍵的三成。mofoim 的定位是「打得不精確也猜得到」，所以我們決定聲調鍵可有可無：沒有聲調鍵的音節被當成「任何一個聲調都有可能」，和誤觸一樣交給語言模型在各種解讀之間選。每個音節各自決定打或不打，不需要切換模式；`Config::toneless_penalty` 設成 `None` 可以回到聲調必打。

這取代 ADR 0003 裡「聲調鍵必須是最後一個鍵」的結論。按鍵序列是唯一事實來源、不事先切字這兩點不變，而且正是它們讓這件事只是「對同一串按鍵多加一種解讀方式」。

## Considered Options

- **另外做一個不打聲調的模式**：使用者要先決定用哪一種，不能只在容易猜錯的字上補聲調。實測只省略一半的聲調時，字的準確率還有 94%，混著打才是這個功能最實用的方式。
- **詞庫另建一份不分聲調的讀音樹**：查詢最快，但資料檔會變大。讀音樹的子節點本來就依音節排序、聲調在最低的位元，同一個音節的各個聲調是連在一起的，查一次就能全部拿到，不需要改資料檔格式。

## Consequences

- 準確率的代價由不打聲調的人自己承擔。2,000 句的實測：完全不打聲調時字的準確率是 90.8%（照常打是 96.9%），整句全對是 64%（照常打是 83%），按鍵少 31%。猜錯的大多是同音字，bigram 語言模型只看前一個詞，分不出來；要再往上，得換更強的語言模型（見 ADR 0002）。
- 照常打聲調的人幾乎不受影響：完全打對時字的準確率差 0.02 個百分點，有誤觸時差 0.23 個百分點；每個按鍵的運算時間從 0.048 毫秒變成 0.056 毫秒。準確率測試把「聲調必打」留著當比較基準，擋住這兩個數字變差。
- 沒打聲調的音節每個扣 0.5 分（log10）。不扣分的話，「打了聲調但有誤觸」的句子會被誤認成沒打聲調；扣太多則猜不出沒打聲調的句子。
- **沒打聲調的音節必須照聲母、介音、韻母的順序按。** ADR 0003 的「同一個字裡的符號不管順序」只在有聲調鍵標出結尾時成立；沒有聲調鍵時，顛倒的「ㄨㄉ」會被當成「ㄉㄨ」，整句的邊界跟著切錯。加上這個限制，字的準確率從 89.5% 升到 90.9%。
- 有聲調的音節仍然不管順序，但顛倒的按鍵現在多了「其實是兩個沒打聲調的字」這種解讀，所以個別句子的結果可能和照順序打時不同。整體準確率沒有下降（測試會擋），只是不再保證一模一樣；聲調必打時仍然保證。
- 容錯在沒打聲調的音節裡比較保守：最多容許 1 次誤觸（容許 2 次的準確率一樣，但慢很多），只有一個符號的音節完全不容錯（它的相鄰鍵幾乎都能自己成一個字，容錯只會多出一大批解讀）。
- **使用者打了聲調，就不會被當成沒打。** 猜不出來的聲調鍵不會孤零零接在「沒打聲調的字」後面，例如關閉容錯時「ㄘㄠˋ」照實顯示，不會變成「草」加上一個多出來的「ˋ」。
- **候選字不會把一個音節從中間切開。** 整句猜測會考慮所有切法（「ㄒㄧㄢ」可以是「先」也可以是「西安」），但較短的候選字不能停在「下一個鍵看起來還屬於同一個音節」的位置，否則選了之後會留下孤立的聲調或韻母，同一個字也會重複出現在候選字裡。使用者真的要在那裡斷開時，補上聲調就可以。
- 空白鍵的規則不變：接在還沒打聲調的音節後面是一聲。也就是說，不打聲調時句子中間打不出空格，要先送出。
- 編輯區仍然照實際按的鍵顯示，不會替使用者補上聲調。還沒被猜成詞的按鍵、以及游標之後的按鍵，除了以聲調鍵為界，同一個位置出現第二個符號（例如又一個聲母）也算下一個音節的開始。
- 以前「還沒打完的音節」會照實顯示成注音並原樣送出；現在只要它本身讀得成字，整句猜測就會是那個字。打到一半時候選字會跟著變動，這是可以不打聲調必然的結果。
- 為了不讓照常打聲調的人變慢，順便做了三個不改變結果的優化：找分數最高的前文時，用「這個詞可能拿到的最高分」提早停止；已經讀到詞尾的進度不再嘗試往下接；丟掉最前面的按鍵（自動送出、釘住）時，和前文無關的讀音解讀留下來重複使用，只重算分數。
